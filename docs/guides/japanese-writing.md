# 日本語の会話・文書・UI表記

常時適用する短い規約の正本は[共有style rule](../../agents/rules/style.md)。
この文書は用例と導入判断を補う。毎回の会話で全文を読む必要はない。

## 表示先で文体を決める

| 表示先                 | 文体・記号       | 例                           |
| ---------------------- | ---------------- | ---------------------------- |
| ownerとの会話          | 常体             | 設定を更新した。             |
| 開発用の記録・報告     | 常体             | Linux側の反映は未確認。      |
| UIの説明・完了通知     | 簡潔な敬体       | 設定を更新しました。         |
| UIの操作案内           | 敬体             | ファイルを選択してください。 |
| ボタン・タブ・項目名   | 短い動作・名詞   | 保存する / 通知設定          |
| 箇条書き・番号付き手順 | 末尾の句点なし   | 設定ファイルを更新           |
| プレーンテキスト欄     | Markdown記号なし | APIキーを入力してください。  |

ボタンを敬体に揃えるために「保存してください」に変える必要はない。
表示先がMarkdownを解釈しない場合は強調やinline codeの記号を文字列に含めない。
日本語と隣接する英単語の間には空白を入れない。
英語の文中の単語間スペースや正式名称は保持する。

箇条書きで文を詰め込みたくなったら項目を分けるか通常の段落に戻す。
段落の句点は残す。引用原文や外部の提出書式には指定された表記を使う。
既存プロダクトの明示的なvoiceがある場合はそれを優先する。

## UI文言の用例

以下はこの環境向けに作成した例。

| 避ける表現                           | 採用する表現                           | 理由                           |
| ------------------------------------ | -------------------------------------- | ------------------------------ |
| 変更を反映させていただきました。     | 変更を反映しました。                   | システム動作の報告を簡潔にする |
| 設定をご確認いただけますでしょうか。 | 設定を確認してください。               | 操作案内を直接伝える           |
| アップロード失敗                     | アップロードできませんでした。         | 本文の文体を敬体に揃える       |
| 不正な操作です。                     | このファイル形式には対応していません。 | 実装から確認できる原因を伝える |
| OK                                   | 変更を保存する                         | 操作の結果を表す               |

最後の2例は実際の原因や操作と一致する場合だけ使う。
再試行できない処理に「もう一度試してください」を足さない。
用語は画面・ヘルプ・エラー間で統一する。

## 調査した既存資産と採否

| 資産                                                                                                          | 用途                           | 今回の判断                   |
| ------------------------------------------------------------------------------------------------------------- | ------------------------------ | ---------------------------- |
| [SmartHRのライティング方針](https://smarthr.design/products/contents/writing-style/)                          | 簡潔な日本語と過剰な敬語の回避 | UI文言の参考として採用       |
| [SmartHRのエラーメッセージ](https://smarthr.design/products/contents/error-messages/overview/)                | 状況と対処の伝達               | 実装で裏付けられる説明を優先 |
| [preset-ja-technical-writing](https://github.com/textlint-ja/textlint-rule-preset-ja-technical-writing)       | 技術文書の文体・誤用検出       | 文書の多いprojectで選択導入  |
| [preset-ai-writing](https://github.com/textlint-ja/textlint-rule-preset-ai-writing)                           | 定型的な装飾や表現の検出       | 補助lint候補                 |
| [sanoakr/ai-skillsのja-proofreading](https://github.com/sanoakr/ai-skills/blob/main/ja-proofreading/SKILL.md) | textlintによる校正workflow     | そのままの導入は見送る       |

SmartHRは製品のライティング指針として参照する。
ownerの会話を常体にすることや箇条書き末尾の句点を省くことはこの環境独自の選択。
外部ガイド全体を共有instructionへ取り込まない。

ja-proofreadingは本文を敬体へ統一する設定を持つためownerとの会話や常体の調査文書と合わない。
長いtrigger列挙と固定の一時環境もそのまま継承しない。
今回必要な規約は既存style ruleに収まるため重複する校正skillは追加しない。

## textlintを追加する場合

文書の多いprojectで依存をlockしCIへ組み込む。
常設toolはdotfilesのNixで管理しグローバルなnpm installは使わない。
project依存として導入する場合は既存のpackage managerを使う。
新しいJavaScript環境ではBunを使う。

- 文体の検査は常体文書と敬体のヘルプで設定を分ける
- コード・引用・URL・識別子を文章校正の対象から除く
- 箇条書きの句点なしと通常段落の句点ありを別々に扱う
- まず変更文書だけを検査して誤検知を確認する
- 自動修正は意味を変えないものだけに限定する

textlintは会話の出力やアプリのすべての文字列を自動で検査するわけではない。
TSX・Swift・翻訳resourceに埋め込まれた文言は抽出またはrender後の確認が必要。
敬語の自然さやエラー原因の正しさはlintだけでは保証できない。

## 反映と確認

共有ruleは`nix/lib/agent-instructions.nix`で結合されClaude・Codex・Geminiへ配布される。
変更の反映には各hostで`dr`を実行し新しいagent sessionを開始する。
既存のsessionには開始時に読み込んだ指示が残る場合がある。

確認時は会話文・ボタン名・エラー本文・plain text欄・箇条書きの5種類を見比べる。
規約ファイルの更新と実際の生成品質の確認は別の検証として扱う。
