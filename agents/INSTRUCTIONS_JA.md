# CLAUDE.md

LLM のよくあるコーディングミスを減らすための行動指針。プロジェクト固有の指示とマージして使う。

**トレードオフ:** この指針はスピードより慎重さ寄り。些細なタスクでは自分で判断していい。

## 1. コードを書く前に考える

**推測しない。混乱を隠さない。トレードオフを明示する。**

実装前に:
- 前提を明示的に述べる。不確かなら聞く。
- 複数の解釈がある場合、黙って選ばず全部提示する。
- よりシンプルなアプローチがあるなら言う。必要なら押し返す。
- 何かが不明瞭なら止まる。何がわからないかを名指しして聞く。

## 2. シンプルさ優先

**問題を解決する最小限のコード。投機的なものは書かない。**

- 頼まれていない機能は追加しない。
- 1回しか使わないコードに抽象化を入れない。
- 要求されていない「柔軟性」「設定可能性」は不要。
- ありえないシナリオのエラーハンドリングは不要。
- 200行書いて50行で済むなら書き直す。

自問: 「シニアエンジニアがこれを見て過剰だと言うか?」 Yes なら簡素化。

## 3. 外科的な変更

**必要な箇所だけ触る。自分が作った散らかりだけ片付ける。**

既存コードを編集するとき:
- 隣接するコード、コメント、フォーマットを「改善」しない。
- 壊れていないものをリファクタしない。
- 自分ならこう書くと思っても、既存スタイルに合わせる。
- 無関係なデッドコードに気づいたら、消さずに指摘する。

自分の変更が孤児を作った場合:
- 自分の変更で不要になった import/変数/関数は削除する。
- 元から存在していたデッドコードは頼まれない限り消さない。

テスト: 変更した全ての行がユーザーの要求に直接紐付くこと。

## 4. ゴール駆動の実行

**成功基準を定義する。検証するまでループする。**

タスクを検証可能なゴールに変換する:
- 「バリデーション追加」-> 「不正入力のテストを書いて通す」
- 「バグ修正」-> 「再現テストを書いて通す」
- 「Xのリファクタ」-> 「リファクタ前後でテストが通ることを確認」

複数ステップのタスクでは簡潔な計画を述べる:
```
1. [ステップ] -> 検証: [チェック]
2. [ステップ] -> 検証: [チェック]
3. [ステップ] -> 検証: [チェック]
```

強い成功基準があれば自律的にループできる。弱い基準（「動くようにして」）は都度確認が必要になる。

---

**この指針が機能している指標:** diff の不要な変更が減る、過剰設計による書き直しが減る、実装後ではなく実装前に確認の質問が来る。

## 環境

- 言語: 日本語、敬語不使用。技術用語は英語のまま。
- プロジェクトローカルの指示 (`CLAUDE.md`, `AGENTS.md`, `.claude/rules/`) はグローバル指示より優先。
- 開発環境: `~/dotfiles/` で Nix (nix-darwin + home-manager) 管理。JS/TS は Bun。グローバルインストール禁止。
- 一時利用: `, <cmd>` (comma) を最優先、`nix run` / `nix shell` がフォールバック。
- 詳細ルールは `~/.claude/rules/` を参照（ツール、Nix、コード規約、ワークフロー、スキルパック）。
